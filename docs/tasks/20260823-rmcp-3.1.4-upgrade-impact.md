# rmcp 0.16.0 → 3.1.4 — surreal-mind upgrade briefing

> ⛔ **PARTLY SUPERSEDED 2026-09-03 (fed-734b8f):** O3 below describes `agent_jobs`, `src/registry.rs`, and the three `call_status`/`call_jobs`/`call_cancel` tools as live code. All were removed in fba5ac2..HEAD (DDL removed from `src/server/schema.rs`; the production table was deliberately left in place, not dropped). The 16-tool `list_tools` layout at line ~104 is now ten tools. Dated analysis; cited line numbers are as of commit `551c1f8`.

**Target:** `rmcp = "0.16.0"` → `rmcp = "3.1.4"` (four major boundaries: 0.16 → 1.0 → 2.0 → 3.0 → 3.1)
**Repo:** `~/Projects/LegacyMind/surreal-mind` on Studio, commit `551c1f8`, version 0.8.2
**Written:** 2026-08-23
**Author:** CC. All source measurements taken read-only over SSH. **No cargo command was run — nothing here is compiler-confirmed.**

## Bottom line

This is a real four-major migration, but the damage is narrow and unusually concentrated. surreal-mind touches rmcp on **50 lines across 24 files in `src/`** (45 of them real API surface, 5 cosmetic) and **19 lines across 5 files in `tests/`**. Two files carry nearly all of it: `src/server/router.rs` and `src/http.rs`. The compile breakage — **42 struct-literal sites**, 27 in build targets and 15 in tests — is repetitive and mechanical: three find-and-replace patterns cover 35 of the 42. Roughly half of surreal-mind's rmcp footprint (`ErrorData`, `ErrorCode`, all of `src/error.rs`) does not change at all, and **none of the four Cargo feature flags break**. What should actually worry you is not the compiler. Three changes are **silent**: rmcp 3.x validates the inbound `Host` header against a loopback-only default allow-list (this will 403 every request through the cloudflared tunnel while compiling perfectly clean), `ProtocolVersion::LATEST` moved from 2025-03-26 to 2025-11-25, and session semantics changed under SEP-2567. Call it **mechanical in the large, needs-design in exactly one place (`src/http.rs`)**, with a mandatory pre-deploy measurement that has nothing to do with Rust.

## BLOCKERS — what stops the build on day one

Ordered by number of sites × how hard the fix is.

### B1. The `#[non_exhaustive]` sweep — 42 struct literals, E0639 — VERIFIED

rmcp applied `#[non_exhaustive]` to most model/wire structs starting at 1.0.0 (and this is **not in the 1.0.0 changelog, which claims "No breaking changes"**). `#[non_exhaustive]` forbids struct-literal construction from a downstream crate outright. **`..Default::default()` does NOT rescue it** — functional-update syntax is a struct expression and is banned too. This is the single most common wrong assumption about this upgrade.

Confirmed `#[non_exhaustive]` in 3.1.4, each read on its own docs.rs page: `Tool`, `ServerCapabilities`, `ToolsCapability`, `Implementation`, `InitializeResult` (= `ServerInfo`), `CallToolRequestParams`, `LoggingMessageNotificationParam`, `Request<M,P>`, `StreamableHttpServerConfig`, `CallToolResult`.

Confirmed **NOT** non_exhaustive (these literals survive): `ErrorData` (carries `#[expect(clippy::exhaustive_structs, reason = "intentionally exhaustive")]`), `ListToolsResult`, `RequestOptionalParam`.

### B2. Removed fields — E0560, independent of B1 — VERIFIED

Even a hypothetically-exhaustive struct would fail on these:

| Field | Sites | Status in 3.1.4 |
|---|---|---|
| `Tool.execution` | 16 | Field gone; `ToolExecution`/`TaskSupport` absent from `rmcp::model` entirely |
| `CallToolRequestParams.task` | **19** (measured by me: 5 in `src/`, 14 in `tests/`) | Field gone; replaced by `input_responses` / `request_state` |
| `StreamableHttpServerConfig.stateful_mode` | 1 | Renamed `legacy_session_mode`, **with changed semantics** |

### B3. `InitializeResult` lost its `Default` impl — VERIFIED

`src/server/router.rs:32`'s `..Default::default()` on the `ServerInfo` literal fails on this ground *separately* from B1. Two independent reasons, one line.

### B4. `ServerHandler::call_tool` return type changed — VERIFIED upstream, downstream shape UNVERIFIED

`Result<CallToolResult, McpError>` → `Result<CallToolResponse, McpError>`. Read directly at `crates/rmcp/src/handler/server.rs` @ `rmcp-v0.16.0:255-259` vs `@rmcp-v3.1.4:482-486`. surreal-mind hand-writes this impl, so there is no macro escape hatch. **`From<CallToolResult> for CallToolResponse` is claimed but was not independently verified, and nobody read `CallToolResponse`'s constructors.**

### B5. Content model rewritten — VERIFIED

`model::Content`, `model::RawContent`, `model::Annotated`, `model::AnnotateAble` are **gone**, replaced by `model::ContentBlock`. `CallToolResult.content` is now `Vec<ContentBlock>`. The `.raw` projection no longer exists. Small blast radius (3 sites) only because 41 of 41 result constructions go through `CallToolResult::structured()`.

### B6. Logging deprecated — WARNING, not error, but effectively a blocker — VERIFIED

`LoggingMessageNotificationParam` and `LoggingLevel` are `#[deprecated(since = "2.0.0")]` under SEP-2577 (still present in 3.1.4, not removed). `Cargo.toml` has **no `[lints]` section** and there is no `deny(warnings)` in `src/` — so rustc will warn, not fail. But the `mcp-development` skill's warnings-are-errors mandate makes this a decision you cannot defer: `test_notification` either gets ported or retired.

### B7. NOT a blocker — say it out loud

**All four feature flags survive verbatim.** `macros`, `transport-io`, `transport-streamable-http-server`, `transport-worker` all exist in 3.1.4 under the same names with byte-identical definitions, and `default = ["base64","macros","server"]` is unchanged. `Cargo.toml:34-37` needs **zero edits**; only the version string on line 33 changes. Do **not** add `default-features = false` — `server` comes from the default set and is load-bearing for `src/http.rs:16-19`.

### 🔴 The silent one — `allowed_hosts` will 403 the tunnel

Not a compile error. VERIFIED upstream: 3.1.4's `Default` sets `allowed_hosts: vec!["localhost", "127.0.0.1", "::1"]`, and `validate_dns_rebinding_headers()` returns **403 Forbidden — "Host header is not allowed"** on mismatch. `host_is_allowed()` returns true only when the vec is empty. **No such check existed in 0.16.0.**

VERIFIED: surreal-mind is public at `https://mcp.samataganaphotography.com/mcp`; `~/.cloudflared/config.yml` on Studio routes that hostname to `http://localhost:8787` with **no `originRequest.httpHostHeader` override**; `src/http.rs` does no Host handling of its own (grep for `HOST`/`Origin`/`header::HOST` matched only `http_bind` at :135/:359/:403/:409), so nothing intercepts ahead of rmcp. surreal-mind's own permissive `CorsLayer` at `:392-393` does **not** satisfy or bypass rmcp's internal check — that check lives inside the nested MCP service.

⚠️ **NOT VERIFIED — and this is the deploy blocker:** what `Host` header cloudflared actually forwards to the origin by default. If it forwards `mcp.samataganaphotography.com`, a mechanically-perfect port that compiles clean will refuse **every** live MCP request. Measure this before deploy. Two options: enumerate the hostname in `with_allowed_hosts([...])` (preferred — keeps a protection 0.16.0 never had), or `disable_allowed_hosts()` to restore old behavior. Do not ship `Default::default()` untouched.

## Q2: Opportunities

### FORCED — the upgrade makes you do these

**F1. Builder-based construction everywhere.** 1.2.0 added "missing constructors for non-exhaustive model types," so every broken literal has a supported replacement. This is why the migration is mechanical rather than a redesign. Effort: **mechanical**.

**F2. Drop dead `execution` / `task` fields.** All 16 `execution: None` and all 19 `task: None` were opting *out*. Nothing is lost, nothing to port to the tasks extension. Effort: **trivial**, rides along with F1.

**F3. Decide `test_notification`'s fate.** See B6. Effort: **needs-design** (small, but a real decision).

**F4. Decide the HTTP session/host posture.** `legacy_session_mode`, `allowed_hosts`, `allowed_origins`, `max_request_body_bytes`, `session_store` — five decisions the compiler will not make for you, on the one code path Sam's live remote MCP endpoint depends on. Effort: **needs-design**.

### OPTIONAL — worth knowing, do NOT bundle into this branch

**O1. `src/oauth.rs` — 409 lines. VERDICT: KEEP. Nothing to delete.**

This was the biggest deletion candidate and the answer is a clean negative. **rmcp 3.1.4 does not ship an OAuth authorization server.** All 36 items under `transport::auth` are **client-side**: `AuthClient`, `AuthorizationManager`, `AuthorizationSession`, `CredentialStore`, `StateStore`, `AuthorizedHttpClient`, `ClientRegistrationResponse` (a client *parsing* a DCR response, not serving one), `WWWAuthenticateParams`. The 3.x additions (`ClientCredentialsConfig`, `JwtSigningAlgorithm`, `OAuthHttpClient`, `AuthorizationCallback`, `ScopeUpgradeConfig`, the `auth-client-credentials-jwt` feature) all extend the *client* flow. rmcp has no token issuance, no RFC 8414 metadata endpoint, no RFC 7591 DCR server, no resource-server validation.

`src/oauth.rs:1-6` and `:34-46` implement surreal-mind as an **issuer** — RFC 8414 metadata, RFC 7591 dynamic registration, PKCE, `OAuthState` holding `bearer_token`/`issuer_url`/`allowed_client_id`/`allowed_client_secret`/`auth_codes`/`refresh_tokens`. rmcp offers nothing that consumes or replaces any of it. The file must survive the upgrade unchanged. This zero is a real zero — the instrument that produced it enumerated all 36 `transport::auth` items.

**O2. Output schemas — a standing gap the upgrade highlights.** 41 of 41 result sites use `CallToolResult::structured()` while 16 of 16 tools declare `output_schema: None`. `Tool::with_output_schema` existed in 0.16.0 too — this is a long-standing gap, not something 3.x unlocks. What *is* new: 1.8.0 validates/strips schemas (#860), and SEP-2106 (3.0.0) relaxes `outputSchema` to accept non-object types (#895). `src/schemas.rs:360` records that output schemas "were defined for rmcp 0.11.0+ but never used."

## ORDERING

Cheapest and most reversible first. Nothing before step 4 touches Rust.

**0. Branch, and preserve rollback.** surreal-mind is live and Sam depends on it. Keep the current release binary; the launchd restart is the last step, not an incidental one.

**1. Measure the cloudflared `Host` header.** The single deploy-blocking unknown, and it needs zero code. Capture one real request's headers at the origin, or set `originRequest.httpHostHeader: localhost` in `~/.cloudflared/config.yml` to make the answer deterministic instead of inferred. Decide the `allowed_hosts` posture from data.

**2. Three 30-second doc checks that could change the plan.** (a) Is `rmcp::ErrorData` still re-exported at the crate root, or only at `rmcp::model::`? (b) Does a plain `async fn` satisfy `MaybeSendFuture`? (c) Does `StreamableHttpService` still mount into axum 0.7?

**3. Read `CallToolResponse` and `ContentBlock`.** Two types nobody in this research read properly, both on the critical path.

**4. Bump the version string only. `cargo check`. Capture the full error list.** This is the real ground truth and it supersedes every count in this document. Expect roughly 32 errors from `Tool` alone (16 sites × 2 classes). **Then `cargo check --features db_integration`** — `tests/mcp_protocol.rs` is invisible without it.

**5. Sweep by repetition, most-repeated first.** (a) `CallToolRequestParams` — 19 sites, one pattern, unblocks the test suite. (b) `Tool` — 16 sites, one pattern, one file. (c) `get_info` — one nested block. Each is independently committable and independently bisectable.

**6. `call_tool` return type + content model.** Decide once: convert `CallToolResult` → `CallToolResponse` at the router boundary (15 tool modules untouched) or at each handler (15 modules change). Router boundary is the smaller diff.

**7. `src/http.rs`, alone, with actual thought.** This is the one that can take down the live endpoint. Do not sweep it.

**8. `test_notification` decision.** Port, retire, or re-implement.

**9. Tests, including `--features db_integration`.**

**10. Acceptance, per `docs/UPGRADE_SUGGESTIONS.md:30`:** release build, tests, `/health`, `tools/list`, one write tool, one read tool, transport log review. **Add:** a real request through the tunnel with the public Host header, and a protocol-version check on the initialize handshake.

⚠️ **Smoke-test trap, measured:** `src/server/router.rs` registers **16** tools; `src/main.rs:89-91` logs `"Loaded 15 MCP tools:"` and omits `journal` from its list. Any post-upgrade check that diffs `tools/list` against that log string produces a false mismatch. Pre-existing bug, unrelated to rmcp.

**Keep every OPTIONAL item out of this branch.** A four-major upgrade whose diff also contains a ToolRouter conversion is a four-major upgrade you cannot bisect.

## WHAT WE COULD NOT ESTABLISH

Read this section as carefully as the rest. Every item below is a place where the plan could be wrong.

**Nothing was compiled.** Zero cargo commands were run (hard constraint — `cargo build`/`check`/`tree` can rewrite `Cargo.lock`, and surreal-mind is live). **Every "this will not compile" in this document is DERIVED from reading type declarations, not observed from rustc.** Error codes (E0639, E0560) are derived from the Rust reference. Step 4 of the ordering exists precisely to replace this document's derivations with measurements.

**The cloudflared `Host` header.** Cloudflare's origin-parameters doc 404'd during research and the search returned nothing decisive. This is the deploy blocker and it is **unresolved**.

**Whether `async fn` still satisfies `MaybeSendFuture`.** The bound change from `+ Send` to `+ MaybeSendFuture` is verified upstream. Whether surreal-mind's four `async fn` trait impls still satisfy it on a default (non-`local`) build is **not verified**. If they do not, the scope grows.

**Whether `StreamableHttpService` still mounts into axum 0.7.** Verified at the dependency level (shared `tower-service ^0.3` seam). **Explicitly not verified at the code level.** Could turn into an axum major migration.

**`CallToolResponse`.** Its constructors were never read. `From<CallToolResult>` is claimed by one source and unverified.

**`ContentBlock`'s exact match arm and text accessor.** Verified that `RawContent`/`Annotated`/`.raw` are gone and `ContentBlock` replaces them. The replacement code shape at `kg_wander.rs:367` is **not verified** — signature not read.

**`ServerCapabilitiesBuilder::enable_tools()` semantics.** Does it produce `list_changed: Some(false)` (current behavior) or `None`? **Unknown.** If a client depends on that field, this is a silent behavior change.

**`Tool::new` arity.** Two research passes disagreed (2 args vs 3). The 3-arg form (`name, description, input_schema`) was read from 3.1.4's rendered source twice and is what this document recommends — **but signature not verified by compilation.**

**`with_title` / `with_description` / `with_website_url` / `with_arguments` / `with_legacy_session_mode` / `with_sse_keep_alive` / `with_allowed_hosts` / `disable_allowed_hosts`.** All read from docs.rs, none compiled.
